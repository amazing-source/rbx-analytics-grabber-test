Knife Farm/ Universe 9610561918/ Read-only investigation, 27 Aug 2026

Selling and placing knives is broken for long-time players

It is not the storage limit. The saved KnifeInventory has nil holes in it, and FindKnife walks it with ipairs — which stops dead at the first hole. One hole at index 12 strands the 3,829 knives behind it.

The fix, in short

  1. In Data/DataInit, make clean() rebuild the inventory as a packed array instead of copying the old numeric keys — with a per-container flag, because PlotCases / PlotKnives are keyed by slot name and must not be renumbered.
  2. In CaseModule.FindKnife (and EquipBestHandler:106), iterate with pairs, not ipairs, so a hole can never brick anything again.

Every affected player repairs themselves on their next join. No migration script, no data loss, roughly six lines changed.

What the player experiences

Symptom

Sell one knife: nothing happens. Sell all: nothing happens. Place a knife on a plot slot: nothing happens. Buying then stalls too, because they cannot free up cash. There is no error — the code path returns silently or logs a warn, so nothing surfaces to the player or to error reporting.

The mechanism

Cause · measured

CaseModule.FindKnife (ServerScriptService.ServerModules.CaseModule:1055) scans the inventory with ipairs. ipairs stops at the first nil. Everything past that index is invisible to it — and FindKnife is the gate on exactly the three actions players report:

Sell one knife
ServerScripts.SellKnives:47
if not itemPos then return end
Sell all knives
ServerScripts.SellKnives:149
continue + warn
Place a knife on a plot slot
ServerModules.MainModule:1094
if not knifePos then … return end

Why the repro failed

Every affected account has Upgrades.Storage = 11 — the maxed upgrade, limit 150 — and between 53 and 3,840 knives. That correlation is real, but it is a correlation with played a lot, not a cause.

Granting yourself 200 knives does not punch a hole. To reproduce it, a duplicate itemID has to have existed in the profile on a past join.

Where the holes come from

Cause · measured

dedupeByItemId → clean() in ServerScriptService.Data.DataInit (~line 144). It rebuilds each container as newContainer[key] = item, keeping the original numeric key and skipping any entry whose itemID is nil or whose ID count is not exactly 1. A skipped entry leaves its index empty — that is the hole.

It also counts IDs across CaseInventory + KnifeInventory + PlotCases + PlotKnives in one shared map, so a duplicated ID deletes both copies. Hole counts in the wild are 1, 2, 4, 6 and 8 — dominated by even numbers, which is the fingerprint of pair-deletion.

Why the fixes you already pushed didn't help anyone

The holes live in the saved profile. clean() re-runs on every join and copies the keys verbatim, so it preserves them. PlayerRemoving only checks that KnifeInventory is still a table — which a holed table is — so it saves happily, forever. Nothing in the codebase compacts it.

A poisoned account stays poisoned across every publish until the rebuild itself is changed.

The patch

ServerScriptService.Data.DataInit

Replace clean() and its four call sites:

local function clean(container, getId, isArray)
    if typeof(container) ~= "table" then return container end

    local newContainer = {}

    for key, item in pairs(container) do
        local id = nil
        if typeof(item) == "table" then
            id = getId(item)
        end

        if id and countMap[id] == 1 then
            if isArray then
                table.insert(newContainer, item)  -- pack: never leave a nil hole
            else
                newContainer[key] = item          -- PlotCases/PlotKnives are keyed by SLOT NAME, do not renumber
            end
        else
            player:SetAttribute(
                "Duped",
                (player:GetAttribute("Duped") or 0) + 1
            )
        end
    end

    return newContainer
end

profile.Data.CaseInventory  = clean(profile.Data.CaseInventory,  function(v) return v and v[3] end, true)
profile.Data.KnifeInventory = clean(profile.Data.KnifeInventory, function(v) return v and v[5] end, true)
profile.Data.PlotCases      = clean(profile.Data.PlotCases,      function(v) return v and v[4] end, false)
profile.Data.PlotKnives     = clean(profile.Data.PlotKnives,     function(v) return v and v[5] end, false)
The isArray flag is load-bearing

PlotCases and PlotKnives are dictionaries keyed by slot name ("Slot3"), not arrays. If those get true, their keys become 1, 2, 3… and every plot breaks on the next join. Only CaseInventory and KnifeInventory get true.

Hardening — optional, but cheap

Make FindKnife tolerant so a hole from any future source can never brick anything again:

-- CaseModule.FindKnife, line ~1055
for i, knife in pairs(profile.Data.KnifeInventory) do   -- was ipairs
    if typeof(knife) == "table"
        and knife[1] == knifeName
        and knife[2] == rarity
        and knife[3] == eventRarity
        and knife[4] == level
        and knife[5] == ItemID then
        knifePos = i
        break
    end
end

Every caller uses the return value either as a truthiness check or as KnifeInventory[pos], so a non-sequential key is fine. Worth making the same change at EquipBestHandler:106.

Why this is safe

Checked before writing it

  • It runs at join, before CaseModule.UpdateKnives builds the tools — and that already iterates with pairs() over the same entries, so nothing changes about what a player sees.
  • Nothing in the codebase stores an inventory index across sessions. EquippedKnives, KnifeAscensions and the tool attributes are all keyed by ItemID, so renumbering is invisible.
  • KnifePower.GetKnifePower falls back to RarityPower.Common and rank 1 — it can never return nil, so a pairs sweep in EquipBestHandler cannot blow up the table.sort comparator.
  • It repairs a second latent bug: today #KnifeInventory (3,846) disagrees with the real entry count (3,840), and CaseModule.GiveKnife compares those two. After packing they match.
Does it wipe data? No.

The keep/drop condition — if id and countMap[id] == 1 — is not touched. The patch changes only where a kept item lands: table.insert instead of newContainer[key]. Same items, packed indices instead of gapped ones.

And on the poisoned accounts that condition drops nothing. Across the full ~510-profile sweep and in detail on 12 accounts: missingId = 0, dupInside = 0, crossDup = 0. Every surviving entry has a unique non-nil id, so every one takes the keep branch. Player_3870112879 goes in with 3,840 knives at indices 1–3846 and comes out with 3,840 knives at indices 1–3840.

The wipe those players suffered already happened, at some past join, when the duplicates still existed. There is nothing left to match on. And if a player does join with a live duplicate, today's code deletes both copies and leaves two holes; the patched code deletes both copies and leaves none. Identical deletion, strictly less damage — there is no input where the patch removes more than the current code does.

Test it in Studio against a copied profile before shipping. DataInit.GetStoreState() returns "Studio_87" in Studio and "Game_1" live, so Studio testing cannot touch live saves by accident.

What this does not do

Limits · stated plainly

It will not bring back knives clean() already deleted

Those are gone from the save. DataStore version history goes back ~30 days if you want to restore a specific whale by hand.

It does not fix whatever creates the duplicate itemIDs

It makes them harmless. The suspects are the plot↔inventory move paths that call AddKnifeToSlot / AddKnife before RemoveKnife without checking its return value — MainModule:1099 and EquipBestHandler:127. If the remove silently fails, the knife ends up in two containers, and on the next join clean() deletes both copies.

Worth considering separately: when a duplicate is found, keep one copy instead of deleting both. Right now a legitimate knife is destroyed alongside its duplicate.

Not proven — treat as hypothesis
  • Which code path creates the duplicate itemID is a candidate list, not a finding. No live duplicate was found in the ~510 profiles read, so the mechanism above is inferred from the pair-deletion fingerprint, not observed directly. Whether new corruption is still being produced is unknown.
  • The first hole was never dated against the v3831 publish. The DataStore version-history read that would settle it hung on throttling and was killed; it is re-runnable in small batches.
Ruled out

The Ascension and Mutation machines. All 12 accounts inspected in detail have KnifeAscensions = {} and empty machine states.

All findings above come from read-only reads of the live Game_1 datastore and a read of the place source on 27 August 2026. No edits were made to the place or to any profile. The hole mechanism and the ipairs break are measured; the duplicate-ID source is not.
